# Development

This doc explains the development workflow so you can get started
[contributing](CONTRIBUTING.md) to Devloop!


## Requirements

You must install these tools:

1. [`go`](https://golang.org/doc/install): The language devloop is
   built in (version >= go 1.19)
1. [`git`](https://help.github.com/articles/set-up-git/): For source control
1. [`make`](https://www.gnu.org/software/make/): For building devloop.

## Getting started

First you will need to setup your GitHub account and create a fork:

1. Create [a GitHub account](https://github.com/join)
1. Setup [GitHub access via SSH](https://help.github.com/articles/connecting-to-github-with-ssh/)
1. [Create and checkout a repo fork](#checkout-your-fork)

Once you have those, you can iterate on devloop:

1. [Build your dev version of devloop](#building-devloop)
1. [Verify changes locally](#verifying-local-changes)
1. [Run devloop tests](#testing-devloop)
1. [Build docs](#building-devloop-docs) if you are making doc changes

When you're ready, you can [create a PR](#creating-a-pr)!

## Checkout your fork

To make local changes to devloop and eventually submit a pull request to the repo,
we recommend [creating your own fork](https://help.github.com/articles/fork-a-repo/).

Once you've done this, clone your fork to your local machine:

   ```shell
   git clone git@github.com:${YOUR_GITHUB_USERNAME}/devloop.git
   cd devloop
   git remote add upstream git@github.com:lucky-tools/devloop.git
   git remote set-url --push upstream no_push
   ```

   _Adding the `upstream` remote sets you up nicely for regularly [syncing your fork](https://help.github.com/articles/syncing-a-fork/)._

## Creating a PR

When you have changes you would like to propose to devloop, you will need to:

1. Ensure the commit message(s) follow the [conventional commits guidelines](https://www.conventionalcommits.org/en/v1.0.0/). The Devloop repo has a bot to check that commit messages follow this style.
2. Ensure the PR description describes what issue you are fixing and how you are fixing it
   (include references to [issue numbers](https://help.github.com/articles/closing-issues-using-keywords/)
   if appropriate)
3. Add unit tests. Unit test coverage should increase or stay the same with every PR.
4. Add integration test if applicable
5. [Create a pull request](https://help.github.com/articles/creating-a-pull-request-from-a-fork/)

Please follow our [small Pull Requests guidelines](./docs/community/small-prs.md) for quicker response time.

### Reviews

Each PR must be reviewed by a maintainer. The integration tests run
automatically via GitHub Actions and must pass for the PR to be submitted.

## Making a config change

Some changes to the devloop code require a change to the devloop config. These changes require a few extra steps:

* Open the latest Config at [pkg/devloop/schema/latest/config.go](https://github.com/lucky-tools/devloop/blob/main/pkg/devloop/schema/latest/config.go) and inspect the comment at [L28](https://github.com/lucky-tools/devloop/blob/main/pkg/devloop/schema/latest/config.go#L28)
* If the line mentions the config version is not released, proceed making your changes.
  ```
  // This config version is not yet released, it is SAFE TO MODIFY the structs in this file.
  ```

* **If the line mentions** the config version is released then, 
  ```
  // !!! WARNING !!! This config version is already released, please DO NOT MODIFY the structs in this file.
  ```
  
  * Run `./hack/new-version.sh` to create a new version.

  * Run `make test` to verify changes.
  
  * Commit these generated changes, and submit a PR.

Once you've done this, merge or rebase your development branch with config changes, including the new config change.
**Any new config changes belong in pkg/devloop/schema/latest/config.go. Do not edit the older config versions.**

* Be sure and update the documentation in `pkg/devloop/schema/<previous_config_version>/upgrade.go` with any additions, removals, or updates you make to the config.

* In case of backwards compatibility issues, update the `Upgrade()` method from the previous config version appropriately. This is usually required when a previously existing field in the config is changed, but **not** when a new field is added.

*Note: the Upgrade() method is called by devloop automatically for older config versions. This can also be done manually by users by running `devloop fix`.*

* Finally, before committing your final changes and opening your pull request, be sure and run `make test` locally. This will regenerate the JSON schemas for the devloop config with your new changes. Commit the resulting changes autogenerated by the scripts.

For more details behind the logic of config changes see [the Devloop config management doc](https://docs.google.com/document/d/e/2PACX-1vRIjLuHL2uZ1OXcV9ZXbOQ7ijmqmeCeOZroCGBGTgstuNaZqoKXwg0KLGt_M-PHBwoVpnsKUhHxJ3Jc/pub).

## Making changes to the Devloop API

We build the API directly through gRPC, which gets translated into REST API through a reverse proxy gateway library. When adding new message types, make changes to [proto/v2/devloop.proto](https://github.com/lucky-tools/devloop/blob/main/proto/v2/devloop.proto), and when adding new enum types, make changes to [proto/enums/enums.proto](https://github.com/lucky-tools/devloop/blob/main/proto/enums/enums.proto). When changing either of these files, you can run `./hack/generate-proto.sh` to generate the equivalent Go code.

## Adding actionable error messages to code.
Devloop has a built-in framework to provide actionable error messages for user to help bootstrap devloop errors.

Also, [v1.19.0](https://github.com/lucky-tools/devloop/releases/tag/v1.19.0) onwards, devloop is collecting failure error codes to help the team get more insights into common failure scenarios.

To take advantage of this framework, contributors can simply use the [`ErrDef`](https://github.com/lucky-tools/devloop/blob/main/pkg/devloop/errors/err_def.go#L32) struct to throw meaningful actionable error messages and
improve user experience.

e.g In this example [PR](https://github.com/lucky-tools/devloop/pull/5953), 
1. The contributor created distinct error codes in [enums.proto](https://github.com/lucky-tools/devloop/commit/59edbda57ae7d2f5d0b53c075497bca480f555f5#diff-b9c28b2c93efad2841c587b3e93d2d83722c9ae26f5f9c961f87e1ca716b0e69R388)
   ```
    // The Kptfile cannot be created via `kpt pkg init`.
    RENDER_KPTFILE_INIT_ERR = 1501;
    // The Kptfile is not a valid yaml file
    RENDER_KPTFILE_INVALID_YAML_ERR = 1401;
    // The Kptfile is not a valid API schema
    RENDER_KPTFILE_INVALID_SCHEMA_ERR = 1402;
   ```
   The `INIT` in this case stands for devloop `INIT` phase which includes, parsing of devloop config and creating a devloop runner. 
   The other valid phases are `BUILD`, `DEPLOY`, `STATUSCHECK`. Complete list [here](https://devloop.dev/docs/references/api/grpc/#statuscode)
2. Run `hack/generate-proto.sh`. These will generate go code and structs for the newly added proto fields.
   ```shell script
    git status
	   modified:   docs-v2/content/en/api/devloop.swagger.json
	   modified:   docs-v2/content/en/docs/references/api/grpc.md
	   modified:   proto/enums/enums.pb.go
	   modified:   proto/enums/enums.proto
   ```
3. The contributor then used these error codes when creating an error in their [proposed code change](https://github.com/lucky-tools/devloop/pull/5953/files#diff-4d18270998dbca6b8378ad2e7720a797044d1357d2c5a7a61f2af56b9f2d1a5dR152).
   They used the constructor `sErrors.NewErrorWithStatusCode` in [pkg/devloop/errors](https://github.com/lucky-tools/devloop/blob/54466ff6983e9fcf977d6e549119b4c1c4dc9e2b/pkg/devloop/errors/err_def.go#L65) to instantiate an object of struct `ErrDef`. 
   `ErrDef` implements the golang `error` interface.
   ```
    err :=  sErrors.NewErrorWithStatusCode(
	proto.ActionableErr{
	  Message: fmt.Sprintf("unsupported validator %q", c.Name),
	  ErrCode: proto.StatusCode_CONFIG_UNKNOWN_VALIDATOR,
	  Suggestions: []*proto.Suggestion{
	    {
	       SuggestionCode: proto.SuggestionCode_CONFIG_ALLOWLIST_VALIDATORS,
	       Action: fmt.Sprintf(
		  	"please only use the following validators in devloop-managed mode: %v. "+
			 "to use custom validators, please use kpt-managed mode.", AllowlistedValidators),
	   },
	  },
    })
   ```

With above two changes, devloop will now show a meaning full error message when this error condition is met. 
```shell
devloop dev 
unsupported validator "foo" please only use the following validators in devloop-managed mode: [kubeval].
To use custom validators, please use kpt-managed mode.
```

## Building devloop

To build with your local changes you have two options:

1. Build the devloop binary:

   ```shell
   make
   ./out/devloop version
   ```

   You can then run this binary directly, or copy/symlink it into your path.

1. Build and install the devloop binary:

   ```shell
   make install
   devloop version
   ```

   This will install devloop via `go install` (note that if you have [manually downloaded
   and installed devloop to `/usr/local/bin`](README.md#install), this will probably
   take precedence in your path over your `$GOPATH/bin`).

   _If you are unsure if you are running a released or locally built version of devloop, you
   can run `devloop version` - output which includes `dirty` indicates you have built the
   binary locally._

## Testing devloop

devloop has both [unit tests](#unit-tests) and [integration tests](#integration-tests).

### Unit Tests

The unit tests live with the code they test and can be run with:

```shell
make quicktest
```

You can also run a larger suite of tests/checks (unit tests, docs check, linters check) using:

```shell
make test
```

In case you see a linter error such as:

```shell
make test
RUN hack/linter.sh
ERRO Running error: no such linter "gocritic"
```

re-run the `hack/install-golint.sh` script to upgrade `golangci-lint`.

### Integration tests

The integration tests live in [`integration`](./integration). They can be run with:

```shell
make integration
```

_These tests require a Docker daemon, a Kubernetes cluster and all the tools
used by every Builder and Deployer, such as kubectl, java, kustomize..._

A way to run the integration tests without installing those tools
and without depending on a Kubernetes cluster is to install
[kind](https://github.com/kubernetes-sigs/kind#installation-and-usage)
and run:

```shell
make integration-in-kind
```

### Running a subset of integration tests

You can select specific integration tests to run via the `INTEGRATION_TEST_ARGS` env var:

```shell
INTEGRATION_TEST_ARGS="-run=TestDev/" make integration
```
